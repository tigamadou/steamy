## 3. Fixtures à créer

Toutes partent de `BASE` par `scenario({ … })` avec `me: LEARNER_ME` (déjà dans `fixtures.ts`, rôle `learner`, `profileStep: null`, sinon `RoleGate` redirige). Un nom dit l'état (français, kebab-case) ; les corps sont typés par `Schemas[…]`. Les fabriques proposées (`parcoursInscrit()`, `arbre()`, `quiz()`, `tentative()`) vont dans `fixtures.ts`.

**Règle du cache.** Les données PUBLIQUES lues avec `getPublicApi` (parcours, catégories, kit, pays) sont mises en cache par le serveur Next et partagées par tous les scénarios : elles ne peuvent donc pas dépendre du scénario. Elles sont servies par un jeu fixe, indexé par slug (`CATALOGUE`, `KITS_PUBLICS`). Ce qui varie par test est l'état de l'apprenant (inscriptions, souhaits, demandes), jamais le parcours lui-même.

### 4.3 Commun à plusieurs écrans

- **CSRF** : les écritures du navigateur (`PUT`, `POST`, `DELETE`) passent déjà par `GET auth/csrf/` ; rien à ajouter, mais le test de contrat vérifie le refus sans jeton pour les nouvelles routes.
- **Pages de destination** : chaque lien du cahier mène à une autre page (demande, parcours, projet, boutique). Le test utilise `expectNoUnhandledCall` ; une route oubliée fait échouer le test au lieu de laisser l'écran dériver. Les pages cibles sont servies par les fixtures de leur écran (par exemple `apprenant-arbre-en-cours` après un Kit Code).
- **Erreurs** : codes lus dans `statuts.ts` (qui lit `apps/api/libs/errors.py`) ; `CONTENT_LOCKED`, `NOT_ENROLLED`, `KIT_CODE_*`, `QUIZ_COOLDOWN` y sont déjà (403 et 429).
- **Test de contrat** : `contract.test.ts` doit valider chaque nouvelle route pour chaque scénario (corps et statut documentés par `openapi.yaml`).

## 6. Dépendances et risques

### 6.1 Risques techniques

| # | Risque | Parade |
| --- | --- | --- |
| 1 | Le catalogue, les catégories, la fiche d'un parcours, le kit et les pays sont lus avec `"use cache"` : le premier scénario qui les lit les fige pour tous les autres, dans le même serveur Next. Un catalogue vide, un parcours en brouillon ou un squelette de fiche ne peuvent donc pas dépendre d'un scénario | Jeu public fixe indexé par slug ; états de l'apprenant dans des routes non cachées ; erreur du catalogue par une valeur sentinelle de la requête (`?q=__erreur500`) ; `REC-APP-348` et `REC-APP-453` passent en unitaire (C). Option plus coûteuse : un second serveur Next (projet Playwright « catalogue-vide ») avec sa propre fausse API ; à décider (§ 6.3, point 9) |
| 2 | Lecteur Vimeo : l'iframe est servie par `player.vimeo.com` | Interception réseau : aucun accès réel. La lecture et l'erreur du lecteur (`REC-APP-384`, `556`, temps lu de `555`) restent en test unitaire `VimeoPlayer.test.tsx` / `LessonVideo.test.tsx` |
| 3 | Horloge : interrogation de la demande toutes les 10 s, du paiement toutes les 3 s, abandon à 2 minutes ; toast d'annulation ; décompte `Retry-After` | `page.clock` (installer, figer après l'affichage, `fastForward`), comme les tests du parent ; jamais d'attente réelle |
| 4 | Dates relatives : les fixtures sont datées de 2026-10-20 alors que l'écran compare à l'horloge réelle (`nextResendAt`, `expiresAt`) | Dates calculées « maintenant + délai » à la résolution de la fixture (technique de `RESERVATION_ACTIVE`) |
| 5 | SMS du parent (`REC-APP-458`, `460`) : seul Mailpit prouve l'envoi | B : étape ajoutée à `deblocage-p3-demande-parent.spec.ts`, helper `support/mailpit.ts` |
| 6 | Quiz : correction décidée par le serveur | La fausse API applique une règle simple et documentée (première réponse = bonne) ; la vraie correction est testée par pytest et par `pedagogie-p1-quiz.spec.ts` |
| 7 | Contrôle du cahier : `scripts/cahier_check.py` ne compte que les `*.spec.ts` ; les scénarios C (unitaire) et E n'ont donc pas d'étape citable | Marquer C comme `manuel` dans le cahier avec le fichier unitaire dans le résultat attendu, ou étendre le script pour accepter un marqueur `unitaire` (décision d'équipe) |
| 8 | `GET catalog/courses/{slug}/` est déclaré `auth: true` dans la fausse API alors que le front l'appelle sans cookie (`getPublicApi`) | Passer à `false` et indexer par slug, en gardant la fiche du scénario pour `COURSE_SLUG` (parent) |
| 9 | Page quittée gardée par Next (Activity) : sélecteurs par rôle, `filter({ visible: true })` ; `goto(…, { waitUntil: "commit" })` pour voir un squelette | Mêmes règles que la vague 2 |

3. Catalogue public fixe, puis Catalogue (`334` à `374`), Fiche (`375` à `409`) et Souhaits (`410` à `435`).

## 7. Définition de terminé

- Les 300 scénarios sont soit `auto` (A, B), soit classés unitaires (C, six scénarios, test nommé), soit E avec une question inscrite au § 6.3 ; aucun scénario n'est « à écrire ».
- `python3 scripts/cahier_check.py` passe : chaque ligne `auto` du cahier a une étape `test.step("REC-APP-… · …")`, aucune étape ne cite une ligne `manuel`.
- `python3 scripts/e2e_matrix.py --check` passe : les douze fichiers de test (`apprenant-mes-parcours`, `apprenant-arbre-parcours`, `apprenant-catalogue`, `apprenant-fiche-parcours`, `apprenant-souhaits`, `apprenant-kit-code`, `apprenant-demande-parent`, `apprenant-paiement-mobile-money`, `apprenant-projet-niveau`, `apprenant-mission`, `apprenant-quiz`, `apprenant-resultats-quiz`) sont inscrits dans `docs/tests/MATRICE-E2E.md`.
- `expectAccessible` (axe WCAG 2 A/AA, aucun défilement horizontal) à chaque état important : liste, arbre, catalogue (défaut, vide, filtré), fiche, souhaits (liste, vide), Kit Code (saisie, échec), demande (chaque statut), projet, niveau, mission, quiz, résultats.
- Projet Playwright `mobile` (360 px) : un scénario dédié par écran (`310`, `322`, `333`, `354`, `369`, `374`, `392`, `409`, `423`, `427`, `435`, `454`, `482`, `496`, `503`, `509`, `518`, `528`, `542`, `553`, `574`, `593`) et les autres états rejoués sur les deux projets.
- Aucun `retry`, `sleep` ni `force: true` ; aucun accès réel à Internet (Vimeo intercepté) ; `contract.test.ts` valide les nouvelles routes de la fausse API pour chaque scénario.
- Pas de donnée partagée entre tests : une session (UUID) par test.
