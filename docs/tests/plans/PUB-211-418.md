## 2. Écrans de la tranche

Convention d'identification : un test Playwright porte une étape `test.step("REC-PUB-nnn · …")` par scénario (`scripts/cahier_check.py`). Pour la stratégie C, voir la décision d'outillage du § 6 : `cahier_check.py` ne lit aujourd'hui que `apps/web/e2e/**/*.spec.ts`.

**Lecture du rendu.** Les pages publiques n'appellent jamais `getServerApi()` : elles utilisent `getPublicApi()` (client anonyme, sans cookie, `'use cache'` par fonction et arguments, délai maximal de 5 s). Conséquence pour la fausse API : le cookie `sessionid=<scénario>.<id>` n'atteint **pas** les lectures du serveur Next. Les données publiques sont donc les mêmes pour tous les tests d'un même serveur Next ; une variante s'obtient (1) par un **slug** réservé pour les fiches, (2) par un **second serveur Next** branché sur un autre « monde » de la fausse API pour les listes sans argument (panne, lenteur), voir § 4. En revanche, les envois de formulaires partent du **navigateur** : le cookie de session du test les atteint, et les scénarios à la façon de `signInAs` fonctionnent pour eux.

Mise en place des mondes dans `apps/web/playwright.fixtures.config.ts` :

- trois `webServer` Next supplémentaires (`next start -p 3101` avec `API_URL=http://localhost:4010/__monde/panne`, `-p 3102` avec `…/lent`), plus le serveur nominal existant sur 3100 ; `PUBLIC_API_URL` identique pour que le navigateur joigne le même monde ;

- tests des mondes `panne` et `lent` en `test.describe.configure({ mode: 'serial' })` : l'état d'un monde est global, et chaque page n'est observable qu'**une fois** par processus à cause de `'use cache'` (la panne n'est jamais mise en cache, la lenteur seulement à la première lecture).

Pourquoi des processus Next distincts : `getPublicApi()` ne transmet ni cookie ni en-tête, et `'use cache'` garde la réponse d'une liste pendant plusieurs minutes dans le processus. Alternative écartée : un interrupteur global dans la fausse API (résultats mélangés par le cache). Alternative à considérer : une variable d'environnement qui coupe le cache dans les fonctions de `lib/` ; elle simplifierait tout mais modifie le code de production (décision de l'équipe, § 6).

**Communs à plusieurs écrans** : le jeton CSRF (`GET auth/csrf/`, déjà en place), le journal des appels (`session.writes()` pour « aucun appel » et « un seul appel »), `expectNoUnhandledCall`, `expectAccessible`. Il n'y a ni session ni rôle à simuler pour cette tranche (visiteur uniquement), sauf REC-PUB-214 (`signInAs` d'un parent et d'un apprenant existants).

**Page d'administration Django** : seul REC-PUB-358 y touche. La fausse API du front ne s'y applique pas (c'est une page rendue par Django). Stratégie : test pytest avec le client de test Django (compte staff, `client.force_login`), parce que la page est déjà couverte par `test_admin_pages_are_served` et que l'e2e réel n'ajouterait que de la lenteur.

**Compléments pytest** (`apps/api/apps/public/tests/test_forms.py`) pour que « texte à relever » du cahier devienne une assertion : message exact pour `schoolName` à 161 caractères, `contactName` à 121, `email` à 255, `name` à 121, `contact` à 255 ; assertion sur l'objet « Nouvelle demande de devis » et sur `+2290197000000` dans l'e-mail d'équipe. ## 6. Dépendances et risques

**Ordre conseillé**
1. Socle : `server.ts` (préfixe de monde, CSRF des `POST` publics), `mondes.ts`, projets Playwright, fichiers `formulaires-publics.ts` et `evenements-publics.ts`.
2. Pages statiques, sans API : 404, légal, à propos, blog, article, hors ligne (rapides, valident le montage).
3. Formulaires : guides/newsletter, aide/contact, écoles/devis (partagent la fausse API des formulaires).
4. Fiche événement (211 à 217).
5. Mondes `panne` et `lent` : erreur réseau, chargement.
6. Jeu D2 du catalogue et parcours transverses, puis accessibilité globale (REC-PUB-418) en dernier.
7. Compléments pytest et B (Mailpit).

**Risques techniques**
- **Cache `'use cache'` du serveur Next** : une liste ne se re-lit pas pendant plusieurs minutes. Un test de lenteur ou de panne ne vaut que pour la première lecture d'un processus. D'où l'ordre fixé dans le monde `lent` et le mode `serial`.
- **Zéro cookie côté serveur** : toute idée de « scénario par cookie » est inopérante pour les lectures publiques ; ne pas la reproduire.
- **Squelette de formulaire** (REC-PUB-356, 382) : l'astuce `javaScriptEnabled: false` doit être validée à l'écriture ; sinon utiliser un `route` qui retarde les fichiers `_next/static`.
- **Mobile 360 px et mondes** : les fichiers `.panne` et `.lent` tournent sur le projet de leur suffixe ; le viewport 360 px est posé dans le test (`page.setViewportSize`).
- **Page quittée gardée montée** (Next 16) : les assertions doivent viser le contenu visible (`filter({ visible: true })`), comme dans les tests actuels.
- **Focus du dialogue hors ligne** (REC-PUB-366) : défaut a11y possible (aucun piège de focus). À traiter comme un bogue si confirmé.
- **Étiquette des tests unitaires** : `scripts/cahier_check.py` ne lit que `apps/web/e2e/**/*.spec.ts`. **Décision d'outillage** : étendre le script à `apps/web/src/**/*.test.ts(x)` et `apps/api/**/test_*.py` (même motif `REC-PUB-nnn ·`), ou marquer les scénarios C comme `manuel` dans le cahier. L'extension est préférable (sinon C ne compte pas comme automatisé).

**Écarts entre le code et le cahier**
- REC-PUB-213, 295, 390 : le titre de l'onglet porte « · Steamy » (gabarit du layout racine) ; le cahier attend le titre seul.
- REC-PUB-366 : le cahier dit « la page masquée n'est pas atteignable » ; le code ne l'empêche pas (à vérifier).
- REC-PUB-283 : la pagination `/blog/page/<n>` n'existe pas (le code le note en commentaire).
- REC-PUB-358 : le cahier ne sait pas si l'équipe reçoit un e-mail ; le code l'envoie (« [Steamy] Nouveau message de contact »), à écrire dans le cahier.
