# Plan de tests · Authentification et inscription, `REC-AUT-231` à `REC-AUT-460`

Plan rédigé sur la branche `chore/plans-tests-scenarios`. Aucun code de test n'est écrit ici : ce document fixe, pour chacun des 230 scénarios, la stratégie, la fixture et le fichier de test. Il s'appuie sur [PLAN-DE-TESTS.md](../PLAN-DE-TESTS.md), [FIXTURES-FAUSSE-API.md](../FIXTURES-FAUSSE-API.md), [FORMAT-CAHIER.md](../FORMAT-CAHIER.md) et sur le cahier `apps/web/e2e/CAHIER-DE-RECETTE.md` (partie 2, lignes 1052 à 1363).

## 1. En-tête

**Tranche** : `REC-AUT-231` à `REC-AUT-460`, soit 230 scénarios, répartis sur 14 écrans du lot 2 : fin de « Reprendre mon inscription » (231 à 246), « Accord reçu », « Mot de passe » de l'apprenant, quatre étapes de profil, « Bienvenue », « Connexion existant », « Consentement refusé », puis l'inscription du parent (« Créer un compte », « OTP », « Mot de passe »).

**Aucun scénario n'est encore marqué `auto` ou `manuel`** dans le cahier pour cette tranche (les lignes sont au format ancien) : la colonne « déjà automatisé » est donc vide. Des tests réels existent, mais sans étape `REC-…` (voir § 5).

### Règles communes aux tests de la tranche

- **Une étape `test.step("REC-AUT-nnn · …")` par scénario**, texte de l'étape = texte de l'action du cahier. Un test regroupe les scénarios qui partent de la même fixture (comme `parent-demande-paiement.fixtures.spec.ts`).
- **Axe à chaque état** (`expectAccessible` de `apps/web/e2e/support/a11y.ts`) : formulaire initial, états d'erreur, chargement, succès.
- **Scénarios « Navigation clavier »** : un test par écran, mêmes aides que `tabTo` de `parcours-p7-accessibilite.spec.ts` (à extraire dans `support/clavier.ts`). **Scénarios « 360 px »** : une étape jouée seulement dans le projet `mobile` (`playwright.fixtures.config.ts`, 360 x 760), comme `onMobile` du test pilote.
- **Réseau coupé** : `page.route(<url de l'API>, route => route.abort())` côté navigateur (tous les envois de formulaire de la tranche partent du navigateur). **Erreur serveur** : fixture avec réponse 500 sur le point d'accès. **Chargement** : réponse retardée de la fausse API, assertion sur l'état du bouton, puis `expect(journal).toHaveLength(1)`.
- **Horloge** : compte à rebours de renvoi du code (60 s) avec `page.clock` (figer après l'affichage du formulaire, comme `freezeClock` du pilote) ; expiration du code (5 min) et de l'inscription (7 jours) avec l'horloge **de la fausse API** (§ 4.1, `/__fx/avancer`), parce que l'expiration est décidée par l'API et non par le navigateur.
- **Destination après connexion ou création du compte** : `/apprenant`, `/parent`, `/enseignant`, `/consentement` ne sont pas servis par la fausse API (hors de cette tranche). Les tests asserent l'URL d'arrivée avec l'aide `stubDestination(page, "/parent")` (§ 4.1) ; l'arrivée dans l'espace avec son contenu réel (H1 « Léa », « Marie », « Koffi ») reste le rôle des tests réels (stratégie B).

## 6. Dépendances et risques

### 6.1 Ordre d'implémentation conseillé

1. **Socle de la fausse API** (§ 4.1) avec `visiteur-anonyme`, `faults.routes`, session modifiable, CSRF public, `stubDestination`. Premier test de validation : `REC-AUT-441` et `REC-AUT-457` (accès direct, aucune donnée).
2. **Reprise, accord, mot de passe de l'apprenant** : `ecrans/inscription-apprenant.ts` (231 à 274). Le parcours entier est vérifiable avec peu de fixtures.
3. **Profil 1 à 4 et Bienvenue** (275 à 347) : référentiels puis `PATCH learner-profile`. Pas de difficulté, volumétrie.
4. **Connexion** (348 à 390) : table de comptes, compteur de tentatives, `next`, panier. À faire avant l'inscription du parent, car 428 et 453 mènent à `/connexion` et `/consentement`.
5. **Consentement refusé** (391 à 404) : trois lignes B déjà couvertes par les tests réels, à marquer seulement.
6. **Inscription du parent : compte, OTP, mot de passe** (405 à 460) en dernier, avec le modèle d'OTP (§ 4.3), puis les ajouts B (414, 433).
7. Marquage du cahier (colonne « Cas » : fixture, cas, `auto`) à chaque PR d'écran, puis `scripts/cahier_check.py`.

### 6.2 Risques techniques

| Risque | Parade |
| --- | --- |
| **OTP** : un front qui compte les essais lui-même masquerait un défaut de l'API | Le front n'en compte aucun (vérifié dans `OtpForm.tsx`) ; la règle vit dans le modèle de la fausse API et dans pytest ; 431 vérifie que la 4e saisie est bloquée **même avec le bon code** |
| **Défi OTP dans l'onglet** (`sessionStorage`) et défi serveur incohérents si le test pose seulement le stockage | Les tests passent toujours par l'écran « Créer un compte » pour créer le défi (fixture `parent-otp-en-cours`) ; seuls les accès directs (441, 457) partent d'un onglet vide |
| **SMS** : le texte du SMS n'est pas simulé | Un seul test B (414, 427, 433) lit Mailpit ; le faux fournisseur de la vraie stack (`SMS_PROVIDER=fake`) suffit, aucun envoi réel |
| **Expiration** (code 5 min, inscription 7 jours) | Horloge de la fausse API (`/__fx/avancer`) ; le compte à rebours du renvoi reste à `page.clock` (deux horloges distinctes : navigateur et fausse API ; 434 les désaccorde exprès pour obtenir `OTP_RESEND_TOO_EARLY`) |
| **Liens à usage unique** | Aucun lien d'invitation ni de réinitialisation dans cette tranche. Seul le **code de reprise** est « montré une fois » (affichage sur l'écran d'attente, autre tranche) ; 234 vérifie qu'il n'est pas réaffiché |
| **React 19 et formulaires** : un champ non contrôlé est réinitialisé après l'action | `submitWith` évite la réinitialisation (231 et P3 le vérifient : l'identifiant reste saisi) ; attendre l'hydratation avant de saisir (`waitFor` du formulaire, comme `tabTo` de P7) |
| **Destinations non servies** (`/apprenant`, `/parent`, `/consentement`) | `stubDestination` (§ 4.1) ; repli : stratégie B pour 349, 350, 352 déjà retenue |
| **Écarts contrat** | `GET auth/learner-signup/` : 404 et 410 non documentés ; `ErrorCodeEnum` côté API (`OTP_DAILY_LIMIT` : le message de l'API est « Nombre maximal de codes atteint pour aujourd'hui. Réessayez demain. », utilisé tel quel par `ParentSignupForm` ; `OtpForm` a son propre texte) : traités comme les écarts 6 du pilote |
| **Doublon d'identifiant** : la fixture `inscription-*` est partagée avec la tranche « Attente » | Un seul fichier `ecrans/inscription-apprenant.ts` ; convenir des noms avec l'auteur de l'autre plan |

## 7. Définition de terminé

- Les 230 lignes `REC-AUT-231` à `REC-AUT-460` sont dans l'un de ces états : étape `REC-AUT-nnn · …` dans un test Playwright (A, B), test pytest ou Vitest cité en remarque (C), ou classées E avec la question du § 6.4 posée au produit. Aucune n'est restée « à écrire ».
- Le cahier est converti pour ces lignes : colonne « Cas » `fixture · cas · auto` (ou `auto, partiel`), `manuel` pour aucune.
- `python3 scripts/cahier_check.py` passe (chaque ligne `auto` a son étape, chaque étape cite un identifiant connu).
- `python3 scripts/e2e_matrix.py --check` passe : les nouveaux fichiers `*.fixtures.spec.ts` sont ajoutés à `docs/tests/MATRICE-E2E.md` pour les écrans `W08`, `W10` à `W16`, `W18`, `WP01` à `WP03` (et `W07`/reprise).
- Axe sans violation à chaque état de chaque écran ; défilement horizontal nul et cibles de 44 px sur le projet `mobile` (360 px).
- `contract.test.ts` vert avec les scénarios de ce plan ; aucun appel non géré (`expectNoUnhandledCall`) dans les tests A.
- Les tests réels du § 5 sont réduits au nominal et portent leurs étapes `REC-…` ; aucun test réel ne duplique un cas déjà joué sur fixtures.
- `pnpm typecheck`, `pnpm test` (Vitest, couverture à 100 % du code modifié) et la CI `e2e-fixtures` passent ; pas de `retry`, de `force: true` ni de `sleep`.
