## 3. Écrans de la tranche

Convention de lecture : les tests A portent une étape `test.step("REC-ENS-nnn · …")` par scénario ; chaque test commence par `signInAs(context, "<fixture>")`. Sauf mention contraire, les scénarios « Afficher en 360 px » sont des étapes jouées sur le projet `mobile` seulement (fonction `onMobile`, comme dans `parent-demande-paiement.fixtures.spec.ts`) avec `expectAccessible(page)` (axe et absence de défilement horizontal) ; les autres états passent aussi `expectAccessible`. « Chargement » = squelette visible grâce à une fixture à lecture lente (`...-lente`, voir section 4) ; « Erreur serveur / réseau » = fixture à lecture en erreur.

## 7. Dépendances et risques

Ordre conseillé d'implémentation :

1. Fausse API : `TeacherWorld`, `TEACHER_ME`, `enseignant-classes.ts` (lecture seulement), `enseignant-parcours.ts`, `enseignant-eleves.ts`, puis écritures et comptages dérivés, puis `enseignant-activation.ts`. Contrat étendu en même temps.
2. Tests de lecture simples : Accueil, Mes parcours, détail, Mes classes (cloisonnement 027 à 031 à la fin).
3. Formulaires : Créer / modifier une classe, Ajouter des élèves.
4. Élèves d'une classe (retrait, annulation), Profil et commentaires (la chaîne 150 à 152).
5. ACT, puis le shell avec ses boucles sur tous les écrans, après les routes minimales des autres écrans.
6. Migration (section 6) et matrice.

Risques :

| Risque | Parade |
| --- | --- |
| Écart sur l'unicité du nom de classe (093) | Décision produit avant d'écrire 092, 093 et 102 ; la fausse API suit le code réel (par enseignant, sans casse). |
| Rendu serveur et état partagé : `router.refresh()` après un retrait ou un commentaire doit relire un état modifié | Un seul `Instance.teacher` ; aucun test ne partage une instance (UUID par test). |
| Dates relatives (« dernière activité … », « expire le … ») | `page.clock.setFixedTime` et dates de fixture exprimées par rapport à `NOW` ; ne jamais comparer à l'horloge du poste. |
| Réseau coupé sur un rendu serveur | `page.route` ne suffit pas : fixture `koffi-api-injoignable` (coupure de socket côté fausse API). Seul « hors ligne » (026) se joue dans le navigateur. |
| Jeton d'activation à usage unique | Fixture avec jeton consommé dans l'instance (007) ; jamais de jeton partagé entre tests. |
| Boucles « tous les écrans » (017, 032, 033) lentes et dépendantes des autres tranches | Les placer dans un seul test en fin de tranche ; marquer l'ordre de livraison. |
| Redirections de garde (021, 022) vers des écrans dont la fausse API n'a pas toutes les routes | Routes minimales ; asserter l'URL, pas le contenu. |
| Cloisonnement : preuve seulement côté écran | Les règles sont en pytest (liste en tête) ; ne pas les recopier dans la fausse API au-delà du 404. |

Questions précises au produit :

1. Unicité du nom de classe (REC-ENS-092, 093, 102) : unique par enseignant sans casse (code actuel, message de l'API « Une de vos classes… »), ou unique dans l'établissement (cahier, message du front) ? Une enseignante peut-elle nommer sa classe comme celle d'une collègue ? La casse compte-t-elle ?
2. Profil d'un élève sans paramètre `classe` (REC-ENS-165) : page « introuvable », ou profil sur l'unique classe commune ? Et si l'élève est dans deux classes de l'enseignante ?
3. Effets non spécifiés d'un retrait ou d'une annulation (REC-ENS-121, 123, 135, 156) : l'élève retiré garde-t-il son compte et sa progression ? Le lien SMS d'une invitation annulée affiche-t-il quoi ? Le retrait d'un élève est-il permis quand l'offre est échue ? Le parent de Yao (inscription non terminée) lit-il le commentaire ?

Question technique à vérifier avant d'écrire REC-ENS-024 : une URL sans route sous `/enseignant/` affiche-t-elle la page 404 racine (hors shell) ?
