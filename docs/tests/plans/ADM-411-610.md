### Pourquoi la quasi-totalité est en pytest

L'administration (`/admin/…`) est une application **Django rendue côté serveur par l'API** (port 8000), avec ses propres formulaires, ses messages d'erreur Django et sa session TOTP. Elle n'est ni dans le front Next.js ni derrière `apps/web/e2e/fausse-api/` : une fausse API HTTP ne peut rien simuler, puisque la page elle-même est la vraie API. Deux options existent : pytest avec le client de test Django (`client.get/post`, session vérifiée par `verified_client(client, GROUPE)` de `apps/api/apps/core/tests/staff.py`) ou Playwright sur la vraie stack. Nous retenons **pytest**, pour quatre raisons :

1. Les cas du cahier sont des règles (validation de formulaire, droits par groupe, calcul d'une taxe, état d'une facture) : le client de test les rejoue en millisecondes, avec la base de test, sans navigateur.
2. Beaucoup de cas sont impossibles ou lents à provoquer sur la vraie stack : jeton DGI expiré, e-MCF inactif, API de la DGI injoignable, écart de montants, concurrence sur un remboursement, jeton à 14 jours pile. Un `monkeypatch` du fournisseur fiscal les rejoue ; le faux fournisseur de la stack e2e ne se pilote que par le nom du client.
3. Un code TOTP ne sert qu'une fois par compte et par fenêtre de 30 s (`apps/web/e2e/support/staff.ts` attend la fenêtre suivante) : chaque scénario Playwright sur l'admin coûte jusqu'à 30 s d'attente et les comptes sont partagés. pytest n'a pas cette limite.
4. Les réglages de taxes sont un singleton global (`PlatformSettings`) : les modifier sur la stack e2e partagée change le total de toutes les commandes des autres specs lancées en parallèle (4 shards). pytest isole chaque test dans sa transaction.

La vraie stack garde un petit nombre de parcours (stratégie B) qui prouvent ce que pytest ne prouve pas : le worker Celery et le faux fournisseur fiscal émettent vraiment la facture, le PDF se télécharge, l'e-mail d'invitation arrive dans Mailpit, le cookie de session du back-office vaut sur l'admin Django et sur Next.js.

## 6. Dépendances et risques

### Prérequis P0 · Reconnaître les tests pytest dans le cahier

`scripts/cahier_check.py` ne lit que `apps/web/e2e/**/*.spec.ts` (`SPECS = sorted(...rglob("*.spec.ts"))`). Un scénario `auto` couvert uniquement par pytest ferait donc échouer le contrôle (« aucun test n'a d'étape qui le cite »). Avant tout : ajouter à `SPECS` les fichiers `apps/api/**/test_*.py`. L'expression régulière `["'`](REC-XXX-nnn) · ` reconnaît déjà `@pytest.mark.rec("REC-ADM-411 · …")` sans autre changement. Ajouter aussi la déclaration du marqueur dans `apps/api/pytest.ini`. `python3 scripts/e2e_matrix.py --check` (écran vers test e2e) n'est pas concerné : les écrans d'administration y figurent en « v1 · admin Django » et se rattachent déjà à des fichiers `admin-*.spec.ts`. Effort : S.

### Risques techniques

- **R1 · Singleton `PlatformSettings` partagé** : les réglages de taxes sont globaux. En pytest, chaque test est dans sa transaction, sans risque. En B, les modifier fausse les totaux des autres specs ; voir R2.
- **R2 · Parcours B et parallélisme** : `admin-parcours-fiscal.spec.ts` doit tourner seul (projet Playwright dédié `fiscal` à `workers: 1`, ou job CI séparé après les autres) et remettre les réglages à zéro dans un `afterAll`. Sans cela, les specs `parent-commandes.spec.ts` et `boutique-checkout-p4.spec.ts` verraient des taxes. Décision d'ordonnancement à prendre avec la CI en 4 shards.
- **R3 · Lecture d'un PDF** : WeasyPrint produit le PDF ; aucune bibliothèque d'extraction de texte n'est dans `requirements.txt`. Pour 591, choisir : `pypdf` en dépendance de test de l'API, ou `pdfjs-dist`/`pdf-parse` en dépendance de développement du web. Le QR code est une image : se contenter de vérifier la présence d'une image, le contenu du QR est testé en unitaire (`fiscal/qr.py`, `test_the_qr_is_inline_svg`).
- **R4 · TOTP à usage unique** : en B, un code ne sert qu'une fois par compte et par fenêtre de 30 s (`staffLogin` attend la suivante). Le parcours B doit utiliser des comptes de démonstration différents de ceux des autres specs ou en créer de neufs (voir R5).
- **R5 · Enrôlement d'un membre neuf (607)** : le secret TOTP d'un membre invité est généré à l'enrôlement (QR code) et affiché sur la page ; le test doit lire ce secret dans la page (texte ou attribut) pour calculer `totp(secret)`. Mailpit fournit le lien d'activation (`mailpit.ts`). L'invitation est à usage unique : une nouvelle adresse par exécution (`finance+<horodatage>@steamy.test`).
- **R6 · Horloge** : seuil de 14 jours (559) : aucun gel de l'horloge nécessaire, `Status.server_time` est injecté. Sinon utiliser `freezegun`/`time-machine` (non installés ; ne les ajouter que si l'injection ne suffit pas).
- **R7 · Concurrence (515)** : on ne teste pas de vrai parallélisme ; on simule par `monkeypatch` du paiement remboursé entre l'affichage et l'enregistrement. À dire explicitement dans la fiche.
- **R8 · Messages Django** : plusieurs résultats attendus citent des messages Django traduits (« Saisissez un nombre. », « Assurez-vous que cette valeur… »). Les tests doivent s'exécuter avec la langue du projet (`LANGUAGE_CODE = "fr"`) ; s'assurer que le client de test n'envoie pas d'en-tête `Accept-Language` contraire.
- **R9 · 571 et 579 en D** : ils exigent le jeton de test de la DGI. Ne jamais l'exécuter en CI (REC-ADM-583). À planifier comme vérification manuelle avant chaque activation en préproduction.

### Ordre d'implémentation conseillé

1. P0 (outillage `cahier_check.py` + marqueur) et fixture `fiscal_dgi` (§ 4).
2. Groupes à fort risque métier : TVA et AIB (2.2), e-MECeF (2.3), factures (2.8), remboursements (2.7), surveillance (2.9) : priorité 2 du plan de tests (« Paiements, taxes, factures »).
3. Permissions (2.5) et audit (2.6) : priorité 1 (« Droits et isolation »). À faire en parallèle de l'étape 2, car indépendant.
4. Réseaux et annonces (2.4), barème (2.1), commandes (2.10).
5. Parcours C (2.11) puis A (487, 552, 585) puis B (le plus coûteux, et le plus fragile).
