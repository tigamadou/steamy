### Pourquoi deux stratégies, une par moteur de rendu

| | Pages `/backoffice/…` (Next.js) | Pages `/admin/…` (Django) |
| --- | --- | --- |
| Qui rend la page | Le serveur Next.js, qui appelle l'API (`/api/backoffice/…`) | Django lui-même, côté API : HTML, formulaires et messages produits par le serveur |
| Fausse API | Oui : elle remplace l'API pour le serveur Next et le navigateur (`docs/tests/FIXTURES-FAUSSE-API.md`) | Sans objet : il n'y a pas d'API entre le navigateur et ces pages, la « vraie » logique est la page |
| Moteur de test retenu | Playwright sur fixtures (`*.fixtures.spec.ts`) | pytest avec le client de test Django, déjà en place : `apps/api/apps/core/tests/staff.py` fournit `staff_member`, `login`, `verified_client`, `code()` |
| Pourquoi | Les états d'écran (erreur 500, OTP expiré, rapport verrouillé dans un autre onglet) ne se provoquent que par fixture | Une réponse HTTP, son HTML, la base, le journal d'audit, les emails et SMS sortants se vérifient en millisecondes, sans attendre la fenêtre TOTP de 30 s (un code ne sert qu'une fois par compte), avec la couverture de branches à 100 % exigée sur le code modifié |
| Ce qui reste en e2e réel (B) | Rien de plus que ce qui existe | Ce qu'un navigateur doit prouver : 360 px, session partagée entre le domaine de l'API et le front, QR code affiché |

Conséquence : les pages Django ne passent jamais par la fausse API ; les 6 scénarios B de la tranche (005, 026, 041, 043, 044, 077) se rattachent aux specs réels existants, pour ne consommer aucun code TOTP de plus.
