## 2. Écrans de la tranche

Convention des tableaux : `REC` = identifiant ; **Strat.** = A, B, C, E (voir § 1) ; une remarque qui cite `pytest` indique que la règle d'API est déjà éprouvée côté API et que le test e2e ne vérifie que l'interface. Mentions communes : « clavier » = Tab/Maj+Tab dans l'ordre logique, focus visible, Entrée soumet, `expectAccessible` (axe WCAG 2 A/AA + absence de défilement horizontal) à chaque état ; « mobile » = projet Playwright `mobile` (360 px) seulement, via une aide `onMobile` comme dans `parent-demande-paiement.fixtures.spec.ts`.

Fixture générique `inscription-visiteur` / `visiteur` : scénario `me: null` posé par `signInAs(context, …)` (cookie `sessionid=<scénario>.<uuid>`, comme `invite-panier`). Sans ce cookie, la fausse API ne conserve aucun état : les tests qui n'ont besoin d'aucun appel peuvent s'en passer.

## 3. Fixtures à créer

Toutes sont des `scenario({…})` (voir `apps/web/e2e/fausse-api/base.ts`) : un nom en français qui dit l'état, **seulement** ce qui les distingue de `BASE`. ## 6. Dépendances et risques

**Ordre conseillé d'implémentation**

1. Socle commun : visiteur, `TEACHER_ME`, mode CSRF des routes publiques, `advanceSignup`, `seedBrowser` étendu, test de contrat.
2. Réinitialisation (4 fichiers de test, 1 fichier de fausse API) : écrans entièrement côté navigateur, état en mémoire ; sert de modèle OTP pour la suite (le parent y revient dans la tranche d'inscription du parent, lignes d'OTP de `/inscription/parent/code`).
3. Activation, puis « Réinitialisé ✓ » (page statique).
4. Accueil, splash et type d'utilisateur (aucune fixture d'API, sauf redirection d'un connecté) ; Identité et Âge.
5. Numéro du parent, Attente, Reprise : le plus lourd (garde serveur, polling, horloge, point de contrôle).
6. Tests B (étapes `REC` ajoutées aux fichiers existants), puis pytest d'alphabet.
7. Marquer `auto` / `manuel` dans le cahier ; renseigner la matrice.

**Risques et difficultés techniques**

| Sujet | Risque | Parade |
| --- | --- | --- |
| OTP et SMS | Le vrai code arrive par Mailpit, ce qui rend les tests lents et dépendants des tâches Celery | Aucun Mailpit en A : code fixe `123456` côté fausse API ; Mailpit seulement en B, avec `expect.poll` (déjà dans `support/mailpit.ts`) |
| Délais d'expiration (5 min, 15 min, 7 jours) | L'horloge Playwright ne déplace que le navigateur, pas la fausse API | Expiration = réponse de fixture (`OTP_EXPIRED`, `RESET_TOKEN_INVALID`, `SIGNUP_EXPIRED`, `INVITATION_INVALID`) ; durée réelle = pytest déjà écrit |
| Plafonds d'essais et de débit | Compter à la main dans la fausse API risque de s'écarter de l'API | Seul le plafond de 3 essais par défi est simulé (règle simple, comme l'API) ; tous les autres plafonds sont des fixtures à réponse fixe ; la règle chiffrée reste dans pytest (`test_settings_drive_the_limits`, `test_daily_limit_per_phone`…) |
| Liens à usage unique | Impossible de « consommer » un lien dans une fixture sans état | `lookup/` ou `accept/` répond `INVITATION_INVALID` ; la vraie consommation est le test B existant (« lien déjà utilisé ») |
| Fragment `#jeton=` | Le serveur ne le voit pas ; difficile à prouver | Assertions sur l'URL après chargement, sur l'en-tête `Referrer-Policy: no-referrer` de la réponse, et sur l'absence du jeton dans tous les chemins du journal d'appels |

| Polling | Intervalle de 15 s, recul jusqu'à 2 min | `page.clock` ; point de contrôle `/__fx/signup` pour changer l'étape |
| Presse-papiers | Permissions variables selon le navigateur | `context.grantPermissions` pour le succès ; `writeText` rejeté via `addInitScript` pour l'échec |
| Navigation « nouvel onglet » | `sessionStorage` est par onglet : le Splash ne se rejoue pas dans le même onglet | Utiliser une nouvelle `page` du même contexte (stockage neuf, cookies partagés) |
| Pages cibles d'une redirection | `/parent`, `/apprenant`, `/enseignant`, `/connexion` se rendent côté serveur avec d'autres routes d'API | Ne jamais suivre la redirection : `context.request.get(…, { maxRedirects: 0 })` ; pour les clics, asserter l'URL sans `expectNoUnhandledCall` |

- Les 230 scénarios sont `auto` dans le cahier (A et B, avec une étape `test.step("REC-AUT-… · …")` dans un fichier `*.spec.ts` ou `*.fixtures.spec.ts`), ou classés `manuel`/« à spécifier » avec leur raison dans la colonne « Résultat attendu » (REC-AUT-087 et 208 : preuve par pytest, à noter `auto, partiel` ou `manuel` selon le choix du produit, car `cahier_check.py` ne lit pas pytest).
