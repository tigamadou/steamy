Règles retenues pour classer :

- Une incertitude sur le seul libellé exact (« texte à confirmer ») ne fait pas passer en E : le test fixe le texte actuel du code, et le produit corrige le cahier si besoin. E est réservé aux cas où le comportement attendu n'existe pas ou n'est pas défini.
- Les écrans de l'enseignant lisent leurs données dans le serveur Next (`getServerApi`, Suspense) ; seules les écritures partent du navigateur (`getBrowserApi`, via `apiCall`). Conséquence pour les scénarios « Couper l'API puis recharger » : sur une lecture serveur, le réseau du navigateur n'y change rien, l'incident se joue par une fixture qui répond 500 (écran d'erreur `app/(enseignant)/enseignant/error.tsx`) ; sur une écriture, `page.route(…, route => route.abort())`.
- Les trois scénarios de cloisonnement par l'interface (`188`, `233`, `279`) sont testés en A (le front montre ce que l'API lui donne) ; la preuve que l'API cloisonne est en B (PT7) et en pytest (déjà en place : `test_classroom_id_of_a_colleague_gives_nothing`, `test_cannot_invite_into_another_teachers_classroom`).

## 2. Écrans de la tranche

Convention : « socle » = la fixture `enseignant-koffi` (§ 3.1). Chaque test d'écran démarre par `signInAs(context, "<fixture>")`, porte une étape `test.step("REC-ENS-nnn · …")` par scénario, passe `expectAccessible` (axe) à chaque état distinct et `expectNoUnhandledCall(session)` en fin de test. Le scénario « mobile » (360 px) est une étape jouée seulement sur le projet `mobile` (aide `onMobile`, comme dans `parent-demande-paiement.fixtures.spec.ts`), avec contrôle de l'absence de défilement horizontal.

## 4. Fausse API à étendre

### 4.1 Socle commun : `ecrans/enseignant-commun.ts` (et `notifications.ts`)

- **Session et rôle** : fixture `TEACHER_ME` (`Schemas["Me"]` avec le rôle enseignant) dans `fixtures.ts` ; `RoleGate role="teacher"` lit `GET accounts/me/`. Un apprenant ou un parent sur `/enseignant` est redirigé : ce garde appartient à la tranche 1-175.
- **État enseignant** : un champ `teacher` dans `Scenario` (`base.ts`) et dans l'`Instance` (`contexte.ts`) : classes, membres par classe, école, évaluations, événements, propositions, candidatures, notifications. Initialisé par `onInstance`, muté par les `POST`/`PATCH`, jamais partagé entre sessions.
- **Routes de lecture** : `GET classrooms/` (paginé, `pageSize`), `GET classrooms/{id}/` et `GET classrooms/{id}/members/` (404 pour toute classe absente de la liste de l'enseignant, jamais 403), `GET classrooms/school/`, `GET referentials/relationships/`, `GET accounts/me/teacher-profile/`.
- **Écritures de compte** : `PATCH accounts/me/teacher-profile/` (met à jour aussi `me`), `POST accounts/me/email/` (règle : `deja.pris@steamy.test` répond `EMAIL_TAKEN` ; `Incorrect2026` comme mot de passe répond `INVALID_CREDENTIALS` ; sinon met `me.email` à jour), `POST accounts/me/password/` (même règle de mot de passe actuel).
- **Notifications avec état** (commun à trois espaces) : `GET notifications/` (filtre `unread`, `page`, `pageSize`, 404 au-delà de la dernière page), `GET notifications/unread-count/` (déjà dans `server.ts` à 0 : le déplacer dans `ecrans/notifications.ts` et le calculer, sinon la route de `server.ts` masque la nouvelle car les routes sont cherchées dans l'ordre), `POST notifications/{id}/read/`, `POST notifications/read-all/`, `GET`/`PATCH notifications/preferences/` (catégories de l'enseignant).
- **Contact** : `POST public/contact-messages/` (201 ; 400 avec `fields.contact` pour `contact-refuse-champ`).
- **Types du corps** : étendre `Body` (`contexte.ts`) avec les requêtes du contrat utilisées (invitation, import, proposition, email, mot de passe, profil) ; le corps reste non validé.
- **Statuts à simuler** : 500 (lecture et écriture), lenteur (`readDelayMs`, `invitationDelayMs`), 404 (classe, événement, page), 409, 429 avec `Retry-After`, 403 `SCHOOL_OFFER_EXPIRED`. Tous passent par `fail()` : le statut vient de `libs/errors.py`. Codes à vérifier dans `statuts.ts` : `ALREADY_IN_CLASSROOM`, `CONSENT_COOLDOWN`, `INVITATION_DAILY_LIMIT`, `LEARNER_QUOTA_EXCEEDED`, `SCHOOL_OFFER_EXPIRED`, `EVENT_ALREADY_PROPOSED`, `IMPORT_TOO_LARGE`, `EMAIL_TAKEN`, `INVALID_CREDENTIALS`.
- **Réseau coupé** : toujours côté navigateur par `page.route(…, route => route.abort())`, sur les seules écritures (invitation, import, proposition, contact, préférence).
- **CSRF** : déjà géré par l'ossature (en-tête `X-CSRFToken`) ; rien à ajouter.

### 4.2 `ecrans/enseignant-invitations.ts`

- `POST classrooms/{id}/invitations/` : 201 `Member` (statut invité) ajouté à `members` de la classe ; erreurs de fixture (`faults.invitation`) ; 403 si offre échue ; 409 `LEARNER_QUOTA_EXCEEDED` si `learnersLeft` = 0 ; décrémente `learnersLeft` et incrémente les places utilisées de `school` (le bandeau de quota change). Journal : un seul `POST` par envoi.
- `POST classrooms/{id}/invitations/import/` : simulateur de règles, sans l'imiter ligne à ligne : un numéro de moins de 8 chiffres donne `PHONE_INVALID` ; une même paire (prénom, nom, téléphone) déjà vue dans l'appel donne `DUPLICATE_ROW` ; un nom présent dans les membres de la classe donne `ALREADY_IN_CLASSROOM` ; au-delà de `learnersLeft`, `LEARNER_QUOTA_EXCEEDED` ; plus de 200 lignes, 413 `IMPORT_TOO_LARGE`. Réponse `ImportResult` (`created: Member[]`, `errors: {line, code, message, data}[]`) ; `message` pris dans `statuts.ts`. Les lignes renvoyées en correction gardent leur `line`.
- Corps : JSON (`rows`) ou `multipart/form-data` (`file`). Voir § 4.3.

### 4.3 Multipart et fichiers

`readBody` de `server.ts` ne lit que du JSON et renvoie `undefined` pour tout autre corps. Pour `198` à `200` il suffit que la route d'import accepte un corps absent si l'en-tête `Content-Type` commence par `multipart/form-data` et renvoie alors le résultat de la fixture (pas d'analyse du fichier : l'analyse réelle est testée en pytest). Journaliser le type de contenu dans `Call` (nouveau champ `contentType`) pour que le test vérifie que le fichier est parti en `multipart/form-data`.

### 4.4 `ecrans/enseignant-evaluations.ts` et `ecrans/enseignant-evenements.ts`

- `GET classrooms/reviews/` : applique `formative`, `summative`, `needsReview`, `classroomId`, `page`, `pageSize` ; `count`, `next` corrects ; 404 au-delà de la dernière page ; `readDelayMs` et `readServerError`.
- `GET events/` (`upcoming`, `pageSize`) et `GET events/{slug}/` (404 inconnu), `GET classrooms/event-applications/`, `POST events/{slug}/proposals/` (corps `classroomId`) : 409 `EVENT_ALREADY_PROPOSED` si la classe figure déjà dans les propositions de l'instance, sinon 201 `Proposal` avec `notifiedCount` = élèves + parents de la classe, et la classe est mémorisée.
- Réutiliser `EVENT` et `EVENT_SLUG` de `fixtures.ts` ; ajouter des fabriques `review()` et `eventApplication()`.

## 6. Dépendances et risques

**Ordre conseillé**

1. Socle fausse API enseignant (§ 4.1) et fixtures `enseignant-koffi`, `enseignant-sans-classe`, à créer avec la tranche 1-175 (même socle).
2. Notifications avec état (commun à trois espaces, débloque aussi parent et apprenant), puis Aide (le plus court, valide le socle).
3. Évaluations, Paramètres.
4. Individuel, puis simulateur d'import et Import par lot.
5. Événements, offre échue (A).
6. Tests C (`196`, `285`, `307`, `344`/`345` à relier) et D (`299`).
7. Parcours B : PT7 (sans dépendance), PT3 et PT4 (prolongent des specs), PT2, PT5, PT1 (le plus lourd).
8. Migrer les anciennes specs (§ 5) une fois les équivalents verts.

**Risques techniques**

1. **Invitation enseignante à usage unique (PT1).** Nadia est activée par `auth/activation.spec.ts` ; PT1 ne peut pas la réutiliser. Solutions : fusionner l'activation dans PT1 (elle sert aussi au mot de passe oublié de l'autre spec, donc un fichier chaîné), ou, mieux, ajouter une seconde enseignante invitée au jeu de démonstration réservée à PT1. À décider avec l'équipe API (jeu `make seed`).
2. **Parents et SMS** : PT1, PT2 et PT3 dépendent de Mailpit (SMS `@sms.test`), d'envois asynchrones (Celery) et de familles neuves (`createFamily`) : toujours `expect.poll` avec délai borné, jamais de pause fixe, et `closeFamily` à la fin.
3. **Expiration à 7 jours** (`326`) : impossible à attendre ; le jeu D2 (Tobi Zinsou) donne l'état, la tâche d'expiration est en pytest.
4. **Horloge** : le décompte de `181` et l'échéance de l'offre se pilotent avec `page.clock` (front) ; côté API réelle, la date d'échéance vient de `valid_until`.
5. **Partage avec la tranche 1-175** : classes, fiche élève, accueil, parcours encadrés alimentent PT6 (`340`, `342`, `346`) et les redirections (`177`, `210`). Les routes et fixtures de socle ne doivent être écrites qu'une fois ; coordonner le nommage `enseignant-koffi` avec l'auteur du plan 1-175.
6. **Routes serveur vs navigateur** : toute lecture de page doit exister dans la fausse API sinon `expectNoUnhandledCall` échoue ; la route `unread-count` déjà présente dans `server.ts` est à déplacer (§ 4.1).
7. **Données uniques** : PT5 (`336`) et `275` ne se rejouent qu'une fois par classe sur la vraie stack : étiquette `@donnees-uniques`, bureau seulement, ou classe créée par le test.
8. **Écarts cahier / code à corriger dans le cahier** : `181` (message et deux plafonds), `195` (4 ou 5 lignes d'aperçu), `197` (message « Le fichier dépasse 200 lignes… »), `278` (état « annulé » absent du code), `300`, `301` (notifications inexistantes), `296` (cible de la notification : le code route par type vers la liste ou la classe).

**Questions au produit (scénarios « à spécifier » ou ambigus)**

1. `300` : une tentative qui passe « À revoir » doit-elle notifier l'enseignant ? Si oui, quel titre, quel texte, quelle cible (`/enseignant/eleves/{id}?classe={id}&tentative={id}` ?). Aujourd'hui l'API ne crée rien.
2. `301` : l'enseignant doit-il recevoir une notification pour une annonce Steamy Events (publication, ou proposition qu'il a lui-même faite) ? Le front sait la router vers `/enseignant/evenements`, l'API ne l'émet pas ; sinon retirer le scénario.
3. `202` : que doit proposer l'écran pour une ligne `LEARNER_QUOTA_EXCEEDED`, `CONSENT_COOLDOWN` ou `INVITATION_DAILY_LIMIT` dans le rapport : seulement lire le message, ou un bouton « Renvoyer plus tard » ? Aujourd'hui ces lignes sont en lecture seule et ne repartent pas.
4. `327` et `345` : quel message afficher au parent qui ouvre un lien d'invitation annulé ou qui accepte une invitation d'une école dont l'offre est échue (le serveur répond `SCHOOL_OFFER_EXPIRED` ou « demande invalide ») ?
5. `181` : plafond d'invitations par jour et par numéro de parent ou par enseignant, et durée du compte à rebours : le cahier cite « le même numéro », l'API a deux plafonds ; confirmer lequel fait foi pour le texte.
